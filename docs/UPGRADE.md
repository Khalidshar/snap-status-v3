# ترقية الإصدار يدويًا

تنفذ شيهانة هذه الأداة على المضيف كـ root بعد موافقة خالد؛ لا تنفذها فحوص GitHub.

```bash
bash scripts/ops/upgrade.sh <commit-كامل-من-٤٠-حرفًا>
```

تتحقق من وحدات صنع المقاطع النشطة وأقفال المكونات الحية قبل الاستنساخ، وقبل
التثبيت، وقبل التفعيل. تتوقف إن وجدت معاينة سناب غير مرسلة وغير ملغاة ولم
تنته صلاحيتها، أو مقطع واتساب محجوزًا لمراجعة الترجمة. تتبع مسار الحالة في
`STUDIO_CONFIG` أو `config/defaults.toml`؛ لا تقرأ ملفات مفاتيح.

الرسالة: «مقطع ينتظر موافقتك؛ النشر يلغيه». الأفضل إكمال مراجعة المقطع أولًا؛
يجوز لخالد اختيار فقدان صلاحية المعاينة القديمة بإضافة `--force-pending`.
هذا الخيار لا يتجاوز وحدة صنع نشطة أو قفلًا حيًا أو سجلًا تالفًا. تبقى
المعاينات والسجلات على القرص ولا تُحذف.

تستنسخ الإصدار إلى `/root/v3-<commit>`، وتثبت بواسطة `release.py` ثم تفعله
بعملية منفصلة. تتوقف عند أي فشل؛ لا تعيد المحاولة ولا تحذف استنساخًا سابقًا.
يبقى المستمعون يعملون أثناء التثبيت مثل الإجراء السابق، لذلك يجب اختيار
وقت خمول وعدم طلب مقاطع أثناء الترقية؛ فحوص ما قبل التفعيل ليست تجميدًا
ذريًا لقبول طلبات جديدة.

بعد التفعيل تعيد تشغيل الخدمات العشر المحددة في الأداة وتنتظر خمس ثوان، ثم
تطبع OLD وCURRENT وحالة كل خدمة وعدد FAILED وأمر الرجوع إلى الإصدار السابق.
عند الإخفاق تُطبع المعلومات نفسها للتشخيص، ولا يتم تراجع تلقائي أو تشغيل مؤقتات.

## كيف يُتحقق منه على الجهاز

قبل أي نشر: `bash -n scripts/ops/upgrade.sh` ثم
`uv run --frozen pytest tests/test_upgrade.py`. جميع حالات الاختبار تستخدم
بيانات مؤقتة وsystemctl وgit وrelease.py مزيفة؛ لا تلمس الحالة الحقيقية.
على المضيف، تتولى شيهانة التنفيذ فقط عند موعد نشر معتمد: ظهور المانع قبل
الاستنساخ عند وجود مقطع أو قفل، ثم OLD/CURRENT والخدمات العشر بعد ترقية خالية.
تراجع معاينة سناب ومقطع واتساب بعد النشر وفق إجراء المشروع.
